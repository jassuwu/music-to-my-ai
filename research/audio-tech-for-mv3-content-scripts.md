# Audio tech for an MV3 content script sonifying streaming LLM DOM mutations

Research date: 2026-08-15. Method: primary-source docs (developer.chrome.com, chromium.org, MDN, W3C, GitHub/npm source), plus Context7 for Tone.js/Strudel docs, plus direct inspection of cloned library source (`Tonejs/Tone.js`, `uzu/strudel` on Codeberg) and real open-source Chrome extensions.

## TL;DR / Recommendation

**Use the raw Web Audio API directly in the content script (default ISOLATED world), with a first-user-gesture unlock pattern, and no offscreen document.** Create one `AudioContext` in the content script, keep it `suspended` until the first trusted `click`/`keydown` anywhere on the host page, then `resume()` it and schedule notes with `OscillatorNode`/`AudioBufferSourceNode` using sample-accurate `currentTime` scheduling. Skip Tone.js unless its synth/effects ergonomics are worth ~80KB gzip; skip Strudel entirely for this use case — its value proposition (cycle/tempo-based pattern language, text-eval REPL) doesn't fit asynchronous, arrhythmic, per-token triggering, and pulling it in means carrying a scheduling model designed for a different problem. Do not route note-triggering through `chrome.offscreen` — the extra `chrome.runtime.sendMessage` round trip and service-worker wake-up cost adds latency and jitter for no benefit, since in-page `AudioContext` playback is already fully supported in a default (isolated-world) content script once unlocked by a user gesture, and every real "sound-on-page-event" extension found in this research plays audio directly in the content script, not through an offscreen document, for exactly this reason.

Full reasoning and citations below.

## 1. Autoplay / user-gesture unlock rules for content scripts

**Verified facts:**

- Chrome's autoplay policy has covered the Web Audio API since Chrome 71: if an `AudioContext` is created before the document has received a user gesture, it starts in the `"suspended"` state, and `resume()` must be called after a user gesture; alternatively the context "will be resumed after a user gesture if `start()` is called on any attached node." Detect this via `AudioContext.state` (`"running"` vs `"suspended"`) or the `statechange` event. — [developer.chrome.com/blog/autoplay](https://developer.chrome.com/blog/autoplay)
- Chromium's own policy doc states there are **no exceptions**: *"Unfortunately, Chrome cannot provide any exceptions to the autoplay policy."* Media with audio may autoplay only if: (1) it's muted/has no audio, (2) **the user tapped or clicked anywhere on the site during the browsing session**, (3) on mobile, the site was added to the Home Screen, or (4) on desktop, the Media Engagement Index (MEI) for that site is high from prior frequent use. — [chromium.org/audio-video/autoplay](https://www.chromium.org/audio-video/autoplay/)
- MDN's canonical guidance is: *"Create or resume context from inside a user gesture."* A user gesture is interpreted as a user-initiated event, "normally a click event." Two supported patterns: (a) construct the `AudioContext` inside the gesture handler itself (state comes up `running` immediately), or (b) construct it earlier and call `audioCtx.resume()` inside the gesture handler if `state === "suspended"`. — [MDN: Web Audio API best practices](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices)
- Chrome's autoplay policy doc explicitly says the definition of "user gesture" for the Web Audio API is still being standardized across browsers and recommends developers *"stick to `click`"* for now. — [developer.chrome.com/blog/autoplay](https://developer.chrome.com/blog/autoplay)
- `Event.isTrusted` is true only for events genuinely generated by the user agent from a real user action, and false for anything dispatched via `EventTarget.dispatchEvent()`. Browser gesture/autoplay-unlock checks key off trusted input events, so a content script cannot fabricate a "click" to unlock audio — it must listen for a real trusted DOM event on the page. — [MDN: Event.isTrusted](https://developer.mozilla.org/en/docs/Web/API/Event/isTrusted)

**How this applies to a content script specifically (synthesis, not a documented Chrome statement — Chrome's autoplay docs never mention extensions or content scripts):**

- A content script executes inside the same tab/frame as the host page. The autoplay/user-activation state that Chrome tracks (item 2 above — "user tapped or clicked anywhere on the site during the session") is a property of the **document/frame**, not of a specific script origin within it. This means a content script's `AudioContext`, even though it's a JS object living in the isolated world, is still subject to the same per-frame autoplay gate as any script on that page — verified indirectly by real extensions (see §3) which all implement an explicit click/keydown-based unlock rather than assuming free access.
- Practical consequence for this project: since ChatGPT/Claude's own web UI already requires the user to click into a message box and press Enter/click Send to start a stream, that click is itself a real trusted `click`/`keydown` on the page **before** any tokens start streaming. A content script can attach a one-time trusted-event listener (`click`, `keydown`) at `document` scope, call `audioCtx.resume()` (or construct the context) inside that listener, and by the time the LLM response begins streaming the context is already `running`. This is the same pattern used by every real extension examined in §3.

**Unlock patterns extensions actually use (verified via source, §3):**
1. Listen for the first trusted `click`/`keydown` on `document`, lazily create/resume the `AudioContext` inside that handler, then detach the listener.
2. `chrome.action` (toolbar icon) click is itself a trusted user gesture available to the **service worker**, which can be used to unlock a not-yet-covered scenario — but note the service worker has no `AudioContext` capability itself (no DOM/Web Audio in MV3 service workers — see §2), so this gesture would have to be relayed to an offscreen document, not consumed directly.
3. An offscreen document, being a hidden, non-tab-visible page, is created and destroyed by the extension itself — there is **no documented Chrome exemption** for offscreen documents from the autoplay policy (checked directly: neither `chrome.offscreen` reference docs nor the "Offscreen Documents in Manifest V3" blog post mention autoplay/gesture exemptions at all). This is a documentation gap, not a confirmed exemption — treat "offscreen documents bypass autoplay" as unconfirmed/inference, not fact.

## 2. MV3 constraints

### CSP and `eval`/`new Function` — the isolated-world vs. extension-page distinction (commonly confused, clarified precisely)

There are actually **three different CSP regimes** in play, and conflating them is the source of most confusion:

1. **Extension pages** (background service worker, popup, options page, and — relevantly — the **offscreen document**) are governed by the manifest's `content_security_policy.extension_pages` directive. In MV3 this may only use `'self'`, `'none'`, `'wasm-unsafe-eval'` (plus localhost for unpacked dev builds) — **`'unsafe-eval'` is disallowed outright**, so `eval()`/`new Function(str)` throw `EvalError` in these contexts. — [developer.chrome.com/docs/extensions/develop/migrate/improve-security](https://developer.chrome.com/docs/extensions/develop/migrate/improve-security)
2. **Content scripts running in the default ISOLATED world** get a *Chrome-imposed* CSP that is separate from both the page's CSP and the extension's manifest CSP: `script-src 'self' 'wasm-unsafe-eval' 'inline-speculation-rules' chrome-extension://<extension-id>/; object-src 'self'`. Chrome's own docs state this "prevents the use of `eval()` as well as loading external scripts." — [developer.chrome.com/docs/extensions/develop/concepts/content-scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)
3. **Content scripts explicitly injected into the MAIN world** (`world: "MAIN"` in `chrome.scripting.executeScript` or the manifest) share the host page's own JS execution context, and are therefore governed by **the page's own CSP**, not the extension's. If the host page's CSP allows `unsafe-eval`, `eval()` works there; if it doesn't, it's blocked — same as any other page script. This is a property of the site, not of Manifest V3.

**Why this matters for the four candidates:**
- **Raw Web Audio API** never calls `eval`/`new Function` anywhere in its own implementation (it's a native browser API) — so it is unaffected by any of the three CSP regimes above and works identically in ISOLATED-world content scripts, MAIN-world content scripts, and extension pages.
- **Tone.js**: direct inspection of the cloned `Tonejs/Tone.js` source tree (`git clone https://github.com/Tonejs/Tone.js.git`, `grep -rn "eval(\|new Function" Tone/`) found **zero** occurrences of `eval()` or `new Function` anywhere in the library source. Tone.js is built entirely on native Web Audio nodes plus its own JS scheduling logic, so it is CSP-safe in a default ISOLATED-world content script.
- **Strudel**: inspected the current source (`codeberg.org/uzu/strudel`, since `github.com/tidalcycles/strudel` now just redirects — confirmed via the repo's own `MOVED_TO_CODEBERG.md`). Grepping every package for real `eval(` calls (not just the English word "evaluate," which appears constantly in comments) found exactly **one** hit in the whole monorepo: `packages/soundfonts/fontloader.mjs:31` — `eval('{' + data)`, used only when parsing legacy MIDI.js-format soundfont JSON, not part of core scheduling. The `@strudel/core`, `@strudel/mini`, and `@strudel/webaudio` packages — i.e., everything needed to build and play patterns **programmatically** via the JS API (`sequence()`, `note()`, `.webaudio()`, etc.) — contain no `eval`/`new Function`. **`eval` only becomes load-bearing if you use `@strudel/transpiler` + `@strudel/repl`**, the pieces that turn a *typed string of live-coding code* into a running pattern (Strudel's REPL parses the user's code with `acorn` into an AST, transforms it, and evaluates the result — this is documented in the technical manual). — [strudel.cc/technical-manual/repl](https://strudel.cc/technical-manual/repl/), source verified directly.
  - Practical implication: if this project used Strudel only as a synthesis/pattern library called from your own JS (never `eval`-ing user-typed code), it would be CSP-safe in an isolated-world content script. It's the REPL/text-evaluation flavor of Strudel that would break there.

### Offscreen Documents API (`chrome.offscreen`)

- `chrome.offscreen.createDocument({url, reasons, justification})` requires a bundled static HTML file, an array of `Reason` enum values (`AUDIO_PLAYBACK`, `CLIPBOARD`, `DOM_PARSER`, `IFRAME_SCRIPTING`, `WEB_RTC`, `USER_MEDIA`, `DISPLAY_MEDIA`, `WORKERS`, `LOCAL_STORAGE`, etc.), and a justification string. — [developer.chrome.com/docs/extensions/reference/api/offscreen](https://developer.chrome.com/docs/extensions/reference/api/offscreen)
- **One offscreen document per extension** (per profile; split-mode incognito gets its own additional one). Attempting to create a second throws.
- The **`AUDIO_PLAYBACK`** reason has a distinct lifecycle rule: Chrome will automatically close the document after **30 seconds without audio actively playing** — all other reasons have no such lifetime limit. This means an offscreen document used for note-triggering would need to be kept "busy" (e.g., a near-silent keep-alive oscillator) or be re-created on demand, adding complexity.
- `chrome.runtime` is **the only** extension API available inside an offscreen document — it has no access to `chrome.tabs`, `chrome.scripting`, etc., and must be driven entirely by messages from the background service worker.
- Content scripts **cannot** message an offscreen document directly; they must `chrome.runtime.sendMessage()` to the background service worker, which either creates the offscreen document (if not already open) and forwards the message, or the content script itself calls `chrome.runtime.sendMessage()` and the offscreen document's own `chrome.runtime.onMessage` listener picks it up (offscreen documents share the extension's runtime messaging bus, so a well-designed message with a `target: "offscreen"` field lets it listen directly — but *creating* the document is still a service-worker-only capability, since `chrome.offscreen` is unavailable to content scripts). Verified in a real extension's source (`MarcuC/custom-veesion-notifications-sound` on GitHub) and Chrome's own reference docs.
- No Chrome documentation found (reference docs or the "Offscreen Documents in Manifest V3" blog post) discusses autoplay-policy interaction for offscreen documents at all — this is a genuine gap in the primary sources, not something I can cite either way.

### Message-passing latency (offscreen/background vs. in-page)

- **No official Chrome-published latency numbers exist** for `chrome.runtime.sendMessage` round trips (searched specifically; none found in developer.chrome.com or chromium.org docs).
- What is documented/discussed in Chromium's own extension developer forums and issue tracker: MV3 service workers are event-driven and get torn down after **~30 seconds of idle time** (sometimes cited as up to 5 minutes for the hard cap), and **must re-register all event listeners synchronously on wake** or they can miss incoming messages. If the service worker has gone idle between LLM tokens (very likely, given how bursty token arrival is and how aggressive Chrome's idle teardown is), the very first `sendMessage` after a gap pays a **service-worker cold-start cost** before the offscreen document ever sees the message — this is not a fixed, documented number, but is a well-attested source of unpredictable added latency in MV3 extensions. — [Chromium extensions group: MV3 Extension Service Worker Async Init When Waking Up](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/bnH_zx2LjQY)
- **Inference** (not directly measured here): even in the warm-service-worker case, a content-script → service-worker → offscreen-document path is two IPC hops before a note fires, versus zero for in-page playback. For a use case emitting several note-triggers per second in response to streaming tokens, this asymmetric, unpredictable latency (worse exactly when the service worker has been idle, which correlates with *gaps* between tokens — the worst possible correlation, since a burst of tokens after a pause would hit the cold-start penalty right when you want tight timing) is a strong argument against routing playback through an offscreen document for this specific project.

## 3. How real "sound-on-page-event" Chrome extensions implement playback

Direct source inspection of `deifos/mechanical-keyboard-click-sim` (GitHub, MV3, "Mechanical Keyboard Sound Simulator") — a content-script-driven, keydown-triggered sound extension, structurally the closest real-world analog to this project's "DOM event → sound" pattern:

- **manifest.json**: `content_scripts` with no `"world"` field (i.e., default **ISOLATED** world), plus a `background.js` service worker that does nothing but log `onInstalled` — all actual audio work happens in the content script, not the background/offscreen layer.
- **content.js** creates its own `AudioContext` (`new (window.AudioContext || window.webkitAudioContext)()`) lazily, the first time it's needed.
- It implements exactly the unlock pattern predicted in §1: a `tryInitAudio(event)` function that **checks `event.isTrusted`** before initializing (`if (event && !event.isTrusted) return;`), attached to both `document`'s `click` and `keydown` listeners, which are removed once the context is successfully resumed.
- Sound is preloaded once via `fetch(chrome.runtime.getURL('click.mp3'))` → `arrayBuffer()` → `audioContext.decodeAudioData()` into an in-memory `AudioBuffer`, played per-keystroke by creating a fresh `AudioBufferSourceNode` from that buffer each time (the standard low-latency Web Audio "preload once, fire-and-forget node per trigger" pattern) — not `new Audio()`/HTMLAudioElement, and not routed through the background or an offscreen document.
- The `click.mp3` asset is declared under `web_accessible_resources` so the isolated-world content script (which can't use `chrome-extension://` URLs implicitly) can fetch it via `chrome.runtime.getURL()`.

Other examples found (not source-inspected in depth, but corroborating the pattern from their own public descriptions):
- **"Keyboard Click Sounds"** (Chrome Web Store) explicitly advertises: *"Sounds are played locally in your browser using Chrome's offscreen audio API"* — this is the one counter-example found of an extension routing keystroke sounds through `chrome.offscreen` rather than in-page, suggesting both approaches are viable in production; no GitHub source was locatable to inspect its unlock/latency handling. — [Chrome Web Store listing](https://chromewebstore.google.com/detail/keyboard-click-sounds/lnpljpdmbfemdompjlnignmjfhpjpmeh)
- **`MarcuC/custom-veesion-notifications-sound`** (GitHub) uses the offscreen-document pattern for a **notification** sound (not a per-keystroke/high-frequency trigger): background service worker creates the offscreen doc with `AUDIO_PLAYBACK` reason and `sendMessage`s it a `target: "offscreen"` payload; the offscreen page's own listener does `new Audio(url).play()`. This is a lower-frequency, latency-tolerant use case (one notification, not several/sec), which is a materially different requirement from this project's continuous per-token triggering.

**Pattern observed across every content-script-based example:** preload audio once (either as a decoded `AudioBuffer` for Web Audio, or a cached `Audio()`/`<audio>` element), gate the very first playback behind a trusted-event listener that resumes/creates the `AudioContext`, and do the actual per-event triggering **synchronously in the content script**, not via message-passing to another extension context — the offscreen-document route in the wild is reserved for lower-frequency, latency-insensitive notification sounds where the 30-second `AUDIO_PLAYBACK` keep-alive window and IPC hop are non-issues.

## 4. Latency and polyphony characteristics

**Raw Web Audio API** (`OscillatorNode` / `AudioBufferSourceNode`):
- MDN's top-level Web Audio API overview states directly: *"Timing is controlled with high precision and low latency, allowing developers to write code that responds accurately to events and is able to target specific samples, even at a high sample rate. So applications such as drum machines and sequencers are well within reach."* — [MDN: Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API)
- Scheduling is sample-accurate via `AudioContext.currentTime` and `node.start(when)`/`stop(when)`; nodes are single-use ("fire and forget" per the Web Audio spec's source-node model) — you create a cheap new node per note rather than reusing/replaying one, which is exactly the shape needed for firing many discrete, independent notes per second. — [W3C Web Audio API 1.1 spec](https://www.w3.org/TR/webaudio-1.1/)
- Zero bundle size (native browser API), zero CSP exposure (see §2), and no scheduling-model mismatch — this is the lowest-latency, most polyphony-friendly, and most MV3-friction-free option of the four.

**Tone.js**:
- Built entirely on Web Audio nodes (confirmed via source inspection, §2), so its raw scheduling floor is the same as native Web Audio, but it layers a **lookahead scheduler**: `context.lookAhead` defaults to **0.1 seconds**, added to `currentTime` to give the audio thread breathing room; this trades ~100ms of added latency for jitter-smoothing. It can be reduced/set to 0, or bypassed via `Tone.immediate()`/`Tone.context.currentTime` directly. `context.latencyHint` also offers `"interactive"` (default-ish, lowest latency), `"playback"` (prioritizes glitch-free sustained output over latency), and `"balanced"`. — [Tone.js Performance wiki, via Context7](https://github.com/tonejs/tone.js/wiki/Performance)
- Requires `await Tone.start()` inside a real click handler before any sound plays (documented in Tone.js's own README) — this is the library-level embodiment of the exact same autoplay-unlock requirement discussed in §1, not a separate mechanism. — [Tone.js README, via Context7](https://github.com/tonejs/tone.js/blob/dev/README.md)
- Verified bundle size: downloaded `tone@15.1.22` from npm directly — the UMD `build/Tone.js` is **340KB minified / ~78KB gzipped** (measured with `gzip -c | wc -c`). That's a real, non-trivial addition to a content script injected into every page load, versus 0 bytes for raw Web Audio.
- Net effect for this project: same underlying scheduling precision as raw Web Audio, plus useful synth/effects abstractions, at the cost of ~78KB gzip and a default ~100ms added latency (tunable down to ~0).

**Strudel**:
- Confirmed via Context7 docs and source: Strudel's core execution model is a **pattern-query loop**, not an event-trigger API — the documented "Basic Scheduling Loop" pattern is `setInterval` polling `pattern.queryArc(begin, end)` at a fixed step (e.g., every 0.5s) to pull "Haps" (scheduled events) out of a cyclic pattern and turn them into `OscillatorNode`s scheduled at their `event.whole.begin`/`.duration`. — [strudel technical manual, via Context7](https://github.com/tidalcycles/strudel/wiki/Technical-Manual)
- This is fundamentally a **tempo/cycle-based** model (TidalCycles' whole reason for existing): patterns are defined over musical cycles and queried in time windows, which is a good fit for live-coded, clock-driven music, but a poor structural fit for **asynchronous, arrhythmic, one-off triggers** driven by unpredictable DOM-mutation timing (LLM token arrival isn't on a musical grid). Using Strudel here would mean either (a) fighting its pattern-query model to shoehorn in ad hoc one-shot events, or (b) dropping to its underlying synthesis engine (`superdough`, which itself just wraps Web Audio nodes) and losing most of what Strudel actually offers. **This assessment is an inference from the documented scheduling model, not a directly-stated Strudel limitation** — Strudel's own docs don't claim it's unsuitable for one-off triggering, they simply don't describe that use case anywhere in the docs surfaced by Context7.
- CSP: as established in §2, Strudel's core/mini/webaudio packages don't use `eval`, but its primary distribution mode (the REPL, `@strudel/repl` + `@strudel/transpiler`) does, and that's the mode all the tutorials and examples target — meaning the path of least resistance with Strudel pulls in the eval-dependent REPL machinery, which would need to be deliberately avoided.
- Given the mismatch in scheduling philosophy, Strudel is **not recommended** for this project regardless of the CSP question.

**`HTMLAudioElement` (`new Audio()` / `<audio>`)**:
- MDN positions `<audio>`/`HTMLMediaElement` as the right tool for straightforward "control playback of an audio track" use cases, and the Web Audio API as the tool for "more complex audio processing" — implying, without stating a specific latency number, that `<audio>` is not the API MDN steers developers toward for precision use cases. — [MDN: Using the Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Using_Web_Audio_API)
- No `AudioParam`-style scheduling API exists on `HTMLAudioElement` — `play()` starts playback at "now," subject to whatever the browser's main-thread/media-pipeline scheduling jank happens to be at call time, with no way to say "start this sample at exactly `t=1.234s`." This structurally rules it out for anything needing tight inter-note timing.
- Every real content-script-based sound extension inspected in §3 uses **decoded `AudioBuffer` + `AudioBufferSourceNode`**, not `new Audio()`, specifically for per-event low-latency playback — corroborating (via revealed preference in production code) that `HTMLAudioElement` is understood by extension authors as the wrong tool for frequent, latency-sensitive triggering, even though no single MDN page was found stating a precise "X ms" figure for `<audio>` startup latency.

## Recommendation

For this project — a content script sonifying streaming LLM tokens with low latency and moderate polyphony (several notes/sec, arrhythmic, arriving as unpredictable bursts) — use **raw Web Audio API, in-page, in the default ISOLATED-world content script**:

1. **Playback location**: Play directly in the content script. Every real content-script-driven sound extension examined does this, and the offscreen-document route adds a `chrome.runtime.sendMessage` round trip plus a possible service-worker cold-start penalty that lands worst exactly when a burst of tokens arrives after a quiet gap — the opposite of what you want. Reserve `chrome.offscreen` for a fallback/edge case only if you ever need audio to keep playing when the tab itself is backgrounded/discarded in a way that kills the content script's context (uncommon for an active chat tab the user is watching).
2. **Autoplay unlock**: Create the `AudioContext` lazily, gated behind the first trusted `click` or `keydown` on `document` (mirroring `deifos/mechanical-keyboard-click-sim`'s `tryInitAudio` pattern, checking `event.isTrusted`). In practice this unlock will already be satisfied by the time streaming starts, because the user has to click into the chat box and hit Enter/Send — a real trusted gesture on the page — before any DOM mutations (and thus any notes) begin. Still, add the listener defensively rather than assuming, since ChatGPT/Claude could change their submit interaction (e.g., voice input, drag-drop) in ways that skip a click.
3. **Library choice**: Skip both Tone.js and Strudel for the core trigger path. Raw `OscillatorNode`/`AudioBufferSourceNode` scheduled via `AudioContext.currentTime` gives sample-accurate timing, zero bundle weight, and zero CSP exposure — the exact profile needed for firing many small, independent notes per second from a content script. If synth/effects ergonomics (envelopes, filters, reverb sends) become worth the code, Tone.js is a safe *addition* later (confirmed `eval`-free, ~78KB gzip, same Web Audio floor, tunable lookahead down to near-zero) — but don't reach for it up front. Strudel's cycle/tempo-based pattern-query scheduling model is a structural mismatch for asynchronous per-token triggering, and its ergonomic path (the REPL) pulls in `eval`-based transpilation that has to be deliberately avoided; there's no compelling reason to adopt it for this project.
4. **Per-note mechanics**: Preload any sample assets once into decoded `AudioBuffer`s at content-script init (as `web_accessible_resources`, fetched via `chrome.runtime.getURL()`), then spawn a fresh `AudioBufferSourceNode` (or `OscillatorNode` for pure synthesis) per triggered note — never `new Audio()`, which has no sample-accurate scheduling and is the wrong tool for this frequency of triggering per every source examined.
